# a-team 시스템 사양 진화 (A-Team Specification Evolution)

본 문서는 Sangrok(주인님)과의 대화를 통해 구체화된 a-team의 차세대 요구사항 및 설계 결정을 기록합니다.

## 1. 요구사항 정의 및 동결 (Requirements & Freezing)
- **전제:** 사용자의 최초 요청은 불분명할 수 있음.
- **프로세스:**
  - 요청 사항을 여러 단계로 분할.
  - 불분명한 부분을 찾아내는 루프를 **최소 2회** 실행.
  - **사용자 경험 (UX):** 방안 B(단계별 통합 보고) 채택. 에이전트들이 내부 루프를 통해 정리된 '확인이 필요한 질문 목록'을 통합하여 주인님께 한 번에 보고함. 주인님의 실시간 피드백 부담을 줄이면서 체계적인 의사결정을 지원함.
  - 에이전트들에게 지시 사항이 충분히 명시적인지 재확인하는 절차를 **1회 이상** 통과.

## 2. 사용자 개입 모드 (Human-in-the-loop Modes)
시스템 실행 시 다음 3가지 모드 중 선택 가능:
1. **Full Auto:** 최종 완료 시까지 반복 수행.
2. **On Verification Failure:** 검증 루프 실패 시에만 개입.
3. **Step-by-Step:** 각 단계별로 명시적 승인 후 진행.

## 3. 팀 구성 및 워크플로우 (Teaming & Workflow)
- **팀 구성:** 초기에는 LLM 추론에 맡기고, 향후 도메인별 템플릿 도입 검토.
- **다중 에이전트 및 상호 비판:**
  - 동일 역할(role)에 여러 에이전트 배치 가능.
  - **상호 비판성:** 옵션 3(라운드 테이블) 방식 지향. 
  - **소통 메커니즘:** 방안 C(동기식 라운드 토론) 채택. 정해진 횟수(예: 2~3회)만큼 모든 참여 에이전트가 동시에 의견을 내고 서로의 내용을 확인하며 수정함. 최종적으로 리더(Planner)가 모든 의견을 취합하여 결론을 내림으로써 효율성과 품질의 균형을 유지함.
- **회귀(Backtracking):** 검증 단계에서 설계 결함 발견 시 '설계' 단계로 롤백.

## 4. 문서화 및 컨텍스트 관리 (Documentation & Context)
- **문서 중심 핸드오버:** 컨텍스트 망각 방지를 위해 단계별 문서를 작성하여 전달.
- **단계별 통합:** 
  - 실행 단계의 에이전트들이 여러 문서를 생성.
  - 해당 단계의 검증 시에는 이를 완수한 **하나의 통합 문서**가 필요함.
  - **통합 주체:** 전용 통합 에이전트(Synthesis Agent)가 리더/플래너(Leader/Planner)와 긴밀히 협력하여 작성. 리더가 방향성을 잡고 통합 에이전트가 상세 내용을 정리하는 구조.
- **최종 문서화:** 모든 단계에 참여했던 에이전트들이 하나의 팀을 구성하여 최종 결과물 작성.
- **컨텍스트 최적화:** 
  - Context caching, 압축된 컨텍스트 간 상호 비교를 통해 중요 정보 유지.
  - **압축 전략:** 방안 C(Hybrid / Comparison) 채택. 중요한 결정 사항은 별도의 'Decision Log'로 명확히 관리하고, 전체 맥락은 요약(Summary)된 컨텍스트로 제공함. 
  - 특히 중요한 내용은 컨텍스트 압축 이후에도 로그 형태로 다시 추가하여 에이전트가 절대로 망각하지 않도록 명시적으로 관리함. 새로운 분석 결과 도출 시 기존 결정 사항과의 정합성을 상호 체크함.

## 5. 도메인 특화 검증 (Domain-specific Verification)
- **연구:** 잦은 상호작용 및 피드백 중심.
- **투자:** 
    - 수익성 검토 효과가 있는 검증 루프 필수.
    - **외부 SW 연동:** 방안 B(화이트리스트 방식) 채택. 에이전트는 직접 CLI 명령어를 생성하는 대신, 시스템에서 사전에 정의한 '안전한 실행 스크립트(예: 백테스팅 도구, 데이터 분석기)'만을 규격화된 매개변수를 통해 호출할 수 있음. 이를 통해 시스템 안정성과 보안을 확보함.
    - **검증 기준:** 방안 B(종합 점수제) 채택. 수익률, 변동성(Sharpe Ratio), 승률, MDD 등을 종합하여 LLM이 전략의 채택 가능성을 추론적으로 판단함. 단순 지표 수치뿐만 아니라 현재 시장 상황에 적합한 전략인지 종합적으로 평가.

## 6. 운영 및 안전 장치 (Operations & Safety)
- **무한 루프 방지:** 
  - 전체 사이클 기준 **최대 5회**로 제한.
  - 5회 초과 시 강제 종료 전 **최종 문제점 요약 리포트** 생성.
  - 이후 명시적 재시작 필요.

## 7. 기술 스택 및 데이터 관리 (Tech Stack & Data Management)
- **개발 언어:** **TypeScript** (Node.js 20+ 환경). 기존 인프라(`services/api`, `services/worker`)와의 정합성 및 타입 안정성을 위해 채택.
- **상태 및 이력 관리 (State & History):**
  - **SSOT:** `.a-team/state/jobs/<job-id>/record.json` (현재 상태 스냅샷).
  - **이벤트 로그:** `events.jsonl` (각 Job/요청별 격리 관리). 모든 작업 이력, 에이전트 간 토론, 결정 사항을 타임스탬프와 함께 기록.
  - **이력 활용 (Checkpointing):** 방안 C(단계별 요약) 채택. 각 작업 단계가 완료될 때마다 리더(Planner)가 해당 단계의 주요 흐름과 결과를 요약하여 체크포인트 형식으로 유지함. 에이전트들은 개별 로그 전체를 읽는 대신, 이 '요약된 타임라인'을 기본 컨텍스트로 활용하여 망각을 방지하고 작업 효율을 높임.
  - **공통 컨텍스트 (Common Context):** 
    - **정의:** 해당 Job 내의 모든 에이전트가 공유하는 최상위 배경 지식. 
    - **운영:** 리더(Planner)만이 직접 업데이트를 수행하여 정보의 권위와 일관성을 유지함.
    - **역할:** CLI 실행 시 에이전트의 시스템 프롬프트나 기본 배경으로 주입되어, 작업 전체를 관통하는 'Base Knowledge' 역할을 함. (단계별 완료 문서와는 엄격히 구분됨)
  - **단계별 완료 문서 (Stage Completion Docs):**
    - **정의:** 특정 작업 단계가 완료되었을 때 생성되는 산출물.
    - **역할:** 다음 단계의 팀에게 전달되는 직접적인 작업 결과물이며, "이전 단계에서 무엇이 이루어졌고, 다음 작업을 위해 무엇을 활용해야 하는가"를 명시함. (에이전트 간의 실무적 핸드오버 문서)
  - **작업 증적:** 각 단계별 생성 문서 및 Decision Log는 해당 작업 디렉토리에 영구 보관.
- **작업 추가 및 확장 (Extensibility):**
  - **Task 정의:** 방안 A(리더의 자율 생성) 채택. 리더(Planner)가 상황에 맞춰 새로운 역할(Role)과 작업 내용을 즉석에서 정의하고 에이전트를 할당하는 자율성을 가짐. JSON 기반의 `TeamTaskTemplate` 형식을 동적으로 생성하여 신규 작업 유형 및 의존성을 즉각 확장함.
  - **에이전트 확장:** `/prompts` 디렉토리에 새로운 역할의 프롬프트 파일을 추가하여 신규 에이전트 즉시 투입 가능.

## 8. 웹 대시보드 기획 (Web Dashboard)
- **목적:** 멀티 에이전트 협업 과정의 투명성 확보 및 실시간 모니터링.
- **레이아웃 구조 (3개 영역):**
  1. **왼편 (Sidebar):** 전체 Job 히스토리 목록. 작업 단위로 관리되어 클릭 시 우측에 상세 정보 표시.
  2. **오른쪽 상단 (Timeline Matrix):**
     - **가로축:** 프로젝트 진행 단계 (Phase: 계획, 분석, 설계, 개발, 검증 등).
     - **세로축:** 해당 단계에 투입된 에이전트(Role) 목록.
     - **인터랙션:** 특정 에이전트 노드 클릭 시 하단 상세 채팅 로그와 연동.
  3. **오른쪽 하단 (Chat/Log View):** 
     - 선택된 에이전트의 구체적인 입력(Prompt), 출력(Completion), 그리고 동료 에이전트와의 토론 내역을 '채팅 리스트' 형태로 시각화.
- **데이터 원천:** `.a-team/state/jobs/<job-id>/events.jsonl` 및 `record.json`을 실시간 파싱하여 대시보드에 반영.
